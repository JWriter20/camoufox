# Firefox auto-update harness

Chases new Firefox releases without a human in the loop, and refuses to hand one
over unless it can prove nothing regressed.

```
detect ──► rebase patches ──► build ──► 7 gates ──► verify ──► pull request
  │            (agent)                                 │
  └── no matching Playwright suite? stop.              └── any regression? issue instead.
```

Nothing is ever merged. The output is a pull request, or an issue explaining why
there isn't one.

**Read [`TRIBAL-KNOWLEDGE.md`](TRIBAL-KNOWLEDGE.md) before changing anything here.**

---

## Why it is shaped like this

**Detection is paired, not greedy.** Playwright trails Firefox by weeks, so
"latest Firefox" and "Firefox that Playwright can test" are different numbers.
Targeting the former means the conformance suite has never seen the browser
you're shipping and every failure it reports is ambiguous. The default `paired`
mode targets the newest Firefox major a released Playwright tag actually pins.
Today that resolves `152.0.4 → 153.0.4` with Playwright `v1.62.0`, and correctly
declines to chase Firefox 155, which no released suite covers yet.

**Two Playwright suites, because they answer different questions.** `tests/` is
a maintained fork of a ~v1.55-era suite carrying ~1800 lines of Camoufox
adaptations; being frozen is what makes it the *regression* gate — every test has
a known prior outcome. The upstream suite is fetched fresh per run at the
resolved tag and is the *conformance* gate. Regenerating `tests/` from upstream
would throw away those 1800 lines, so the harness never does.

**The proof is computed, not reported.** Gates write evidence files. `verify.py`
reads those files and the baseline and decides. No gate reports its own verdict,
and the agent's opinion of its work reaches nothing. The pull-request body is
generated by `verify.py` in a job that never ran an agent.

---

## Proving there is no regression

`verify.py` fails the run on any of these. Each corresponds to a way a broken
build could otherwise look green:

| Failure | The shortcut it closes |
| --- | --- |
| A required gate wrote no evidence | Deleting or short-circuiting a check |
| Evidence stamped with another run id | Reusing a previous run's green result |
| A baseline-passing test is now failing | The actual regression |
| A baseline-passing test is now *absent* | Deleting the failing test |
| An unexpected new failure | Quietly absorbing upstream's new coverage |
| Fewer tests collected than `min_tests_collected` | A suite that collapsed at import and "passed" 40 tests |
| A waiver with no reason, no expiry, or an expired one | Excuses becoming permanent |

Regressions are decided per test *identity*, never by totals — a suite whose
counts improved can still have swapped which tests pass.

`harness/tests/` asserts every row of that table. They run on every pull request
via `.github/workflows/lint.yml`.

## The gates

| Gate | What it proves | Needs |
| --- | --- | --- |
| `patches_apply` | All ~49 patches apply to the new tree, per `scripts/patch.py` | — |
| `build` | `./mach build` produces a binary for linux x86_64 | — |
| `patch_guards` | `tests/patches/*.py` — each spoofing behaviour still works | binary |
| `build_tester` | 8 fingerprint profiles, graded per individual check | binary |
| `playwright_vendored` | No regression against the frozen suite | binary |
| `playwright_upstream` | Conformance against upstream's suite at the resolved tag | binary |
| `pythonlib` | The Python package's own tests | — |
| `sundial` | Stealth report, aggregate numbers only | binary, credentials |

A patch that applies is not a patch that works — `patch_guards` is what
distinguishes the two, which is why policy allows it zero failures.

## Setup

### Secrets

| Name | Kind | Needed for |
| --- | --- | --- |
| `SUNDIAL_USERNAME` | secret | the stealth gate |
| `SUNDIAL_AUTOMATION_KEY` | secret | the stealth gate (already set) |
| `OPENAI_API_KEY` | secret | patch repair with `codex` |
| `ANTHROPIC_API_KEY` | secret | patch repair with `claude` |
| `SUNDIAL_REPORT_AGE_RECIPIENT` | **variable** | optional: an encrypted copy of the full stealth report |

### About the model credential

Use a **dedicated OpenAI API key** with a hard spend cap, not a ChatGPT
subscription.

A $20 ChatGPT Plus plan has no CI-usable credential. Codex CLI can sign in with
a ChatGPT account, but that writes an OAuth token to `~/.codex/auth.json`, and
using it here means storing a full account credential in a public repository's
Actions environment, where the refresh token rotates out from under you and the
workflow starts failing for reasons that look unrelated. Plan limits are also
sized for interactive use, and a rebuild loop will exhaust them.

The `CODEX_AUTH_JSON` secret is supported anyway — it is your account — but it is
not the default and not the recommendation. A metered key is revocable,
scopeable to a project, capped, and is the only mode designed for this.

You can also run with `HARNESS_AGENT=none`. Everything still detects, builds,
gates and reports; the harness just stops at the first rejecting patch and opens
an issue rather than trying to fix it. That is a reasonable place to start.

### Recording the first baseline

Regression detection needs a floor. From a known-good release:

```bash
python3 -m harness.gates.pythonlib
python3 -m harness.gates.patch_guards      --binary path/to/camoufox-bin
python3 -m harness.gates.build_tester      --binary path/to/camoufox-bin
python3 -m harness.gates.playwright_vendored --binary path/to/camoufox-bin
python3 -m harness.gates.playwright_upstream --tag v1.62.0 --seed-expectations \
                                             --binary path/to/camoufox-bin
python3 -m harness.gates.sundial           --binary path/to/camoufox-bin

python3 -m harness.verify --update-baseline \
  --firefox-version 152.0.4 --camoufox-release beta.31 --playwright-tag v1.62.0
```

Then triage `baseline/playwright-upstream-expectations.yml` — replace every
`reason: TRIAGE` with a real one — and set
`gates.playwright_upstream.bootstrap: false` in `policy.yml`. Until you do, that
gate reports without gating.

## Running it by hand

```bash
python3 -m harness.detect_release --json          # what would it do?
python3 -m harness.detect_release --mode latest   # ignore the Playwright pairing

# The full rebase, without an agent:
HARNESS_AGENT=none python3 -m harness.repair_patches --target-version 153.0.4

# One gate, against an existing build:
python3 -m harness.gates.playwright_vendored --binary path/to/camoufox-bin

# The verdict, from whatever evidence exists:
python3 -m harness.verify
```

`workflow_dispatch` takes `force_version`, `agent`, `mode` and
`seed_expectations` if you'd rather drive it from the Actions tab.

## Security

The workflow is three jobs so that the job holding credentials and the job
holding write access are never the same job:

- **`detect`** — read-only, no secrets.
- **`update`** — runs the agent and every gate with `contents: read`. The agent
  physically cannot push, comment or tag. The model credential is scoped to the
  single step that invokes the agent; the sundial credential is scoped to the
  single step that needs it, introduced only after the agent has finished, so it
  is never in the environment of a model-driven step. Results leave as artifacts.
- **`propose`** — has write access, runs no agent, holds no model credential, and
  recomputes `verify.py` from the downloaded evidence rather than trusting the
  earlier job's status.

The agent is confined to `patches/`, `additions/`, `settings/`, `upstream.sh`
and `docs/`. Writes elsewhere are reverted; writes to `harness/`, `tests/`,
`build-tester/`, `service-tester/` or `.github/workflows/` void the run outright
rather than being reverted, and the workflow re-checks this from outside the
process that could have been influenced.

Sundial's report is redacted at `gates/sundial.py::redact()` before anything
touches disk — the artifact carries counts and HMAC'd ids, never a vector name,
value or source. Set `SUNDIAL_REPORT_AGE_RECIPIENT` to also keep an
`age`-encrypted copy of the full report that only you can open.

**Residual risk worth naming:** the agent can edit `patches/`, and those patches
become the browser that later runs with the sundial cookie. Path confinement
does not make a hostile model safe — it makes an *unreliable* one safe. The
mitigations are that the model is one you chose, the sundial credential is
low-value and rotatable, and nothing merges without you reading the diff.

## Limits

- **linux x86_64 only.** Windows and macOS are cross-compiled by the release
  workflow. Gating a Firefox bump doesn't need them, and seven targets would not
  fit in a GitHub-hosted job.
- **One Firefox major per run** (`release_detection.max_major_jump`). A two-major
  jump is a different job and wants a human.
- **`service-tester` is not wired in.** It needs live residential proxies, which
  are not something to put in a public repository's CI.
- **GitHub-hosted runners cap at 6h/job** and 10 GB of cache. The build job is
  capped at 350 minutes with an 8 GB ccache. If cold builds start timing out, a
  self-hosted runner is the fix — the gates are unchanged by where they run.
